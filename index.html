01存储过程创建与参数定义

存储过程（Stored Procedure）是一组预编译的 T-SQL 语句集合，存储在数据库中，可通过名称调用。存储过程具有以下优势：

  • 性能优化：首次执行时编译并缓存执行计划，后续调用直接复用
  • 安全控制：可通过授权控制访问，隐藏表结构
  • 模块化：业务逻辑封装，减少网络流量
  • 事务完整性：可在过程内部管理事务

脚本原文

CREATE PROCEDURE dbo.p_mold_auto_apply_v4_bak
    @is_auto INT = 0
AS
BEGIN
    SET NOCOUNT ON;
    -- 存储过程主体逻辑...
END
GO

通用完整语法 通用扩展

CREATE [ OR ALTER ] PROCEDURE [schema_name.]procedure_name
    [ { @parameter data_type } [ VARYING ] [ = default_value ] [ READONLY ] [ OUT | OUTPUT ] ]
    [ ,...n ]
AS
BEGIN
    -- T-SQL 语句
END

固定写法 生产环境标准存储过程头部模板

CREATE OR ALTER PROCEDURE dbo.p_procedure_name
    @param1 INT = 0,        -- 带默认值的输入参数
    @param2 VARCHAR(100) = NULL,  -- 可空参数
    @result INT OUTPUT      -- 输出参数
AS
BEGIN
    SET NOCOUNT ON;           -- 固定写法：关闭行数返回，提升性能
    SET XACT_ABORT ON;         -- 固定写法：运行时错误自动回滚事务

    BEGIN TRY
        BEGIN TRANSACTION;
        -- 核心业务逻辑
        COMMIT TRANSACTION;
    END TRY
    BEGIN CATCH
        IF @@TRANCOUNT > 0
            ROLLBACK TRANSACTION;
        -- 错误处理
    END CATCH
END
GO

关键风险点：

  • 缺少 SET NOCOUNT ON：每条语句执行后都会向客户端发送 DONE_IN_PROC 消息，造成网络开销，严重影响性能
  • 缺少 SET XACT_ABORT ON：当发生运行时错误（如约束冲突）时，事务不会自动回滚，导致数据不一致。SET XACT_ABORT ON 会确保任何运行时错误都自动回滚整个事务
  • 参数默认值陷阱：@is_auto INT = 0 中若调用者传 NULL，则值为 NULL 而非 0。默认值仅在调用者"不传参数"时生效，传 NULL 则保持 NULL
  • GO 分隔符：GO 不是 T-SQL 语句，是 SSMS/sqlcmd 工具的批处理分隔符。在动态 SQL 或应用程序代码中不能使用 GO
  • OR ALTER：SQL Server 2016 SP1+ 才支持 CREATE OR ALTER，旧版本需先 IF EXISTS DROP 再 CREATE

调用存储过程的两种方式：

-- 方式1：按位置传参
EXEC dbo.p_mold_auto_apply_v4_bak 1;

-- 方式2：按名称传参（推荐，更安全）
EXEC dbo.p_mold_auto_apply_v4_bak @is_auto = 1;

02变量声明与赋值

T-SQL 中的局部变量以 @ 开头，必须先 DECLARE 声明后才能使用。变量作用域从声明处开始，到声明所在的批处理/存储过程结束。

  • 标量变量：存储单个值，如 @count INT
  • 表变量：存储多行多列数据，如 @tbl TABLE(...)
  • 全局变量以 @@ 开头，是系统预定义的，如 @@ROWCOUNT、@@TRANCOUNT

SET vs SELECT 的关键差异（高风险）：

-- 场景：查询无匹配行时
DECLARE @v1 INT = 100, @v2 INT = 100;

-- SET 方式：无匹配行时，@v1 被设为 NULL
SET @v1 = (SELECT col FROM tbl WHERE 1=0);  -- @v1 = NULL

-- SELECT 方式：无匹配行时，@v2 保持原值 100！
SELECT @v2 = col FROM tbl WHERE 1=0;      -- @v2 = 100（未变！）

这个差异是很多 Bug 的根源：当 SELECT 赋值的查询没有匹配行时，变量不会被重置为 NULL，而是保持之前的值。如果之前的值来自上一次循环迭代，就会导致数据错误。

固定写法 游标循环中变量赋值的标准模式

DECLARE @emp_no VARCHAR(20), @line_no VARCHAR(20);

OPEN cur;
FETCH NEXT FROM cur INTO @emp_no, @line_no;

WHILE @@FETCH_STATUS = 0
BEGIN
    -- 每次循环处理当前行数据
    FETCH NEXT FROM cur INTO @emp_no, @line_no;
END
CLOSE cur;
DEALLOCATE cur;

03事务管理（BEGIN / COMMIT / ROLLBACK）

事务（Transaction）是作为单个逻辑工作单元执行的一系列操作。事务具有 ACID 四大特性：

  • Atomicity（原子性）：全部成功或全部回滚
  • Consistency（一致性）：事务前后数据保持一致状态
  • Isolation（隔离性）：并发事务互不干扰
  • Durability（持久性）：提交后永久保存

@@TRANCOUNT 是全局变量，记录当前连接的活动事务数量。每 BEGIN TRANSACTION 加 1，每 COMMIT 减 1，ROLLBACK 清零。

脚本原文

BEGIN TRY
    BEGIN TRANSACTION;
    -- ... 核心业务逻辑 ...
    COMMIT TRANSACTION;
END TRY
BEGIN CATCH
    -- Step 1: 回滚事务
    IF @@TRANCOUNT > 0
        ROLLBACK TRANSACTION;
    -- ... 后续错误处理 ...
END CATCH;

完整事务语法 通用扩展

-- 显式事务
BEGIN TRANSACTION [tran_name];
    -- DML 语句
COMMIT TRANSACTION [tran_name];   -- 提交
-- 或
ROLLBACK TRANSACTION [tran_name];  -- 回滚

-- 保存点（嵌套事务中部分回滚）
BEGIN TRANSACTION;
    SAVE TRANSACTION save_point1;
    -- 某些操作
    ROLLBACK TRANSACTION save_point1;  -- 只回滚到保存点，不回滚整个事务
COMMIT TRANSACTION;

事务控制语句一览

语句作用对 @@TRANCOUNT 的影响
BEGIN TRANSACTION开始一个显式事务+1
BEGIN TRAN同上（简写）+1
COMMIT TRANSACTION提交事务-1
ROLLBACK TRANSACTION回滚整个事务清零为 0
SAVE TRANSACTION设置保存点不变
ROLLBACK TRAN save_point回滚到保存点不变（不改变 @@TRANCOUNT）
SET IMPLICIT_TRANSACTIONS ON隐式事务模式执行某些语句时自动 BEGIN

固定写法 TRY/CATCH + 事务的标准模板（生产必备）

BEGIN TRY
    BEGIN TRANSACTION;

    -- 业务逻辑

    COMMIT TRANSACTION;
END TRY
BEGIN CATCH
    IF @@TRANCOUNT > 0
        ROLLBACK TRANSACTION;

    -- 记录错误、通知等
    THROW;  -- 重新抛出错误给调用者
END CATCH;

事务常见风险：

  • 嵌套事务陷阱：SQL Server 实际上没有真正的嵌套事务。内层 BEGIN TRAN 只增加 @@TRANCOUNT，最外层的 ROLLBACK 才真正回滚所有操作。内层 COMMIT 只是减计数
  • 忘记在 CATCH 中检查 @@TRANCOUNT：如果 TRY 块中在 BEGIN TRAN 之前就出错，CATCH 中 ROLLBACK 会报"没有对应 BEGIN TRANSACTION"的错误。必须先 IF @@TRANCOUNT > 0
  • 长事务锁定：事务持有锁的时间越长，阻塞其他会话的可能性越大。应尽量缩短事务范围
  • 缺少 SET XACT_ABORT ON：未设置时，某些错误（如约束冲突）只会终止当前语句而非整个事务，导致后续语句继续执行在"脏"事务中
  • 事务中调用外部存储过程：如果被调用的存储过程内部也有 BEGIN/COMMIT，且出错时未正确回滚，可能导致事务计数不一致

SET XACT_ABORT ON 的作用：当设置为 ON 时，如果 T-SQL 语句产生运行时错误，整个事务将自动终止并回滚。这是生产环境存储过程的必备设置。在自动点模脚本中通过 SET NOCOUNT ON 和 TRY/CATCH 配合实现事务安全。

04错误处理（TRY / CATCH）核心重点

TRY...CATCH 是 SQL Server 2005+ 引入的结构化错误处理机制，类似于 C#/Java 的 try-catch。当 TRY 块中的代码发生错误时，控制权立即转移到 CATCH 块，TRY 块中剩余代码不再执行。

CATCH 块中可用的错误函数：

函数返回内容
ERROR_MESSAGE()完整的错误消息文本
ERROR_NUMBER()错误号（整数）
ERROR_SEVERITY()错误严重级别（0-25）
ERROR_STATE()错误状态号
ERROR_PROCEDURE()发生错误的存储过程名
ERROR_LINE()发生错误的行号
XACT_STATE()事务状态：1=可提交, -1=不可提交, 0=无活动事务

CATCH 块 6 步重点讲解

Step 1：回滚事务 固定写法

IF @@TRANCOUNT > 0
    ROLLBACK TRANSACTION

这是 CATCH 块的第一要务。进入 CATCH 说明 TRY 块出错，必须先回滚未提交的事务释放锁资源。@@TRANCOUNT > 0 的判断必不可少——如果错误发生在 BEGIN TRANSACTION 之前，此时没有活动事务，直接 ROLLBACK 会报错。

Step 2：游标清理 固定写法

IF CURSOR_STATUS('global', 'auto_mod_cur') <> -3
   OR CURSOR_STATUS('local', 'auto_mod_cur') <> -3
BEGIN
    CLOSE auto_mod_cur;
    DEALLOCATE auto_mod_cur;
END;

CURSOR_STATUS 返回值含义：-3 表示游标不存在/已释放。当游标可能已打开时（错误发生在游标循环中），必须先 CLOSE（关闭已打开的游标）再 DEALLOCATE（释放游标引用）。如果游标已经关闭但未释放，只需 DEALLOCATE。同时检查 global 和 local 两种作用域确保覆盖。

CURSOR_STATUS 返回值完整说明：

返回值含义
1游标已打开，至少包含 1 行
0游标已打开，但不包含任何行
-1游标已关闭
-2游标不可用（未分配或已释放）
-3指定名称的游标不存在

Step 3：系统错误日志

EXEC dbo.p_sys_raiserror;

调用自定义的系统错误记录存储过程，将错误信息写入日志表。这是一个业务约定：所有存储过程出错时都调用此过程统一记录错误日志，包含错误号、错误消息、存储过程名、行号等。该过程内部通常通过 ERROR_NUMBER()、ERROR_MESSAGE() 等函数获取错误详情。注意：必须在 Step 1 回滚事务之后调用，否则日志写入可能被回滚。

Step 4：获取错误信息

DECLARE @send_id VARCHAR(50) = NEWID();
SELECT @rem_20 = ERROR_MESSAGE();

声明变量并通过 ERROR_MESSAGE() 获取完整的错误文本。NEWID() 生成唯一标识符，用于消息跟踪。注意 @rem_20 的类型是 VARCHAR(5000)，足以容纳大部分错误消息。错误信息将作为通知消息体发送。

重要：ERROR_MESSAGE() 等错误函数只能在 CATCH 块内部使用。如果需要在 CATCH 块外部使用错误信息，必须先赋值给变量保存。

Step 5：查询通知接收人

SELECT @recipient = STRING_AGG(b.emp_no, ',')
FROM tb_mes_msg_type a
    LEFT JOIN tb_mes_msg_type_users b
        ON a.msg_type_code = b.msg_type_code
WHERE a.msg_type_code = 'MJTBCC'

使用 STRING_AGG（SQL Server 2017+）将多个员工编号聚合为逗号分隔的字符串，如 '10001,10002,10003'。使用 LEFT JOIN 确保即使没有配置接收人，消息类型记录也存在。消息类型代码 'MJTBCC' 对应"模具提醒"场景。

Step 6：发送多渠道通知

EXEC zgRdp.dbo.p_sys_call_make_msg
    @MsgTile = @remark1,
    @Body = @rem_20,        -- 错误消息
    @WeixinPush = 1,       -- 微信推送
    @PcPush = 1,           -- PC推送
    @AndroidPush = 1,       -- Android推送
    @RecUsers = @recipient,
    @temp_id = 'DxOjZaab_bWL6mwzjVLq5bWXnFycR35MH2DwQAgJimQ',
    ...

跨数据库调用（zgRdp.dbo.）发送通知。@WeixinPush = 1, @PcPush = 1, @AndroidPush = 1 同时启用三个推送渠道，确保运维人员能及时收到告警。@temp_id 是微信模板消息ID。错误消息体 @Body 直接使用 ERROR_MESSAGE() 的结果，让接收人看到具体错误内容。

固定写法 生产级 CATCH 块完整模板（基于自动点模脚本抽象）

BEGIN CATCH
    -- 1. 回滚事务（必须第一步执行）
    IF @@TRANCOUNT > 0
        ROLLBACK TRANSACTION;

    -- 2. 清理游标（如果使用了游标）
    IF CURSOR_STATUS('global', 'cur_name') <> -3
       OR CURSOR_STATUS('local', 'cur_name') <> -3
    BEGIN
        CLOSE cur_name;
        DEALLOCATE cur_name;
    END

    -- 3. 记录错误日志
    EXEC dbo.p_sys_raiserror;

    -- 4. 获取错误信息
    DECLARE @errmsg VARCHAR(5000) = ERROR_MESSAGE();

    -- 5. 查询通知接收人
    DECLARE @recipient VARCHAR(2000);
    SELECT @recipient = STRING_AGG(b.emp_no, ',')
    FROM tb_mes_msg_type a
        LEFT JOIN tb_mes_msg_type_users b
            ON a.msg_type_code = b.msg_type_code
    WHERE a.msg_type_code = 'YOUR_MSG_CODE';

    -- 6. 发送通知
    EXEC zgRdp.dbo.p_sys_call_make_msg
        @MsgTile = '操作出错',
        @Body = @errmsg,
        @WeixinPush = 1, @PcPush = 1, @AndroidPush = 1,
        @RecUsers = @recipient,
        @temp_id = 'your_template_id',
        @MsgType = 0, @SheetNo = '', @LevelId = 0,
        @SendUser = '', @RecRole = '', @RecSql = '',
        @MenuId = '', @define1 = '', @define2 = '',
        @define3 = '', @define4 = '', @define5 = '',
        @extend_field = '';
END CATCH;

CATCH 块关键风险：

  • 错误函数时效性：ERROR_MESSAGE() 等函数必须在 CATCH 块首次执行的语句中使用。如果 CATCH 块中先执行了其他语句（如 EXEC），错误信息可能被覆盖。在自动点模脚本中，Step 3 先执行了 EXEC dbo.p_sys_raiserror，但该存储过程内部会自行捕获错误信息。如果直接在主 CATCH 块中使用，应确保 ERROR_MESSAGE() 是最早调用的
  • 事务状态检查：更严谨的做法是使用 XACT_STATE()。返回 -1 表示事务不可提交（必须有 ROLLBACK），返回 1 表示可提交，返回 0 表示无活动事务
  • 通知发送失败：如果 Step 6 的通知发送过程本身出错，CATCH 块没有嵌套 TRY/CATCH 保护，会导致"错误处理中出错"。生产环境应考虑在通知外层加 TRY/CATCH
  • 游标名称硬编码：CURSOR_STATUS 需要传入游标名称字符串，如果游标名改了但忘了同步修改 CATCH 块，清理会失效
  • STRING_AGG 兼容性：SQL Server 2017 之前不支持 STRING_AGG。旧版本需用 STUFF(...FOR XML PATH('')) 替代
  • @recipient 为 NULL：如果查询无结果，@recipient 为 NULL，传给通知存储过程可能导致参数无效

05条件与流程控制（IF / ELSE / WHILE / CONTINUE / BREAK）

T-SQL 提供以下流程控制语句：

  • IF...ELSE：条件分支
  • WHILE：循环
  • BEGIN...END：语句块（类似 C/Java 的 {}）
  • BREAK：跳出循环
  • CONTINUE：跳过本次循环剩余部分，进入下次循环
  • RETURN：无条件退出存储过程/函数
  • GOTO：跳转到标签（不推荐使用）
  • WAITFOR：延迟执行

脚本原文

-- 时间验证：3点-6点、15点-18点期间不允许人工触发
IF @is_auto = 0
BEGIN
    IF (DATEPART(HOUR, GETDATE()) BETWEEN 3 AND 5)
    OR (DATEPART(HOUR, GETDATE()) BETWEEN 15 AND 17)
    BEGIN

    -- 循环体

临时表风险提示：

  • 忘记删除临时表：存储过程多次调用时，如果临时表已存在，SELECT INTO 会报错。必须先检查并删除
  • OBJECT_ID 检查写法：OBJECT_ID('tempdb..#temp') 是检查 tempdb 中临时表的正确写法。如果写成 OBJECT_ID('#temp') 在当前数据库中找不到
  • 表变量大数据量性能差：表变量没有统计信息，优化器预估行数为 1。如果实际数据量大，执行计划会严重偏差。超过 100 行建议用临时表
  • 临时表与事务：临时表参与事务。如果 CREATE TABLE #temp 在事务内执行，ROLLBACK 后临时表仍然存在但数据被回滚。在 CATCH 块中不需要显式 DROP（会话结束自动清理），但建议手动 DROP
  • 全局临时表 (##)：多个会话可见，当一个会话创建全局临时表后，其他所有会话都能访问。最后一个引用它的会话断开后自动删除。使用不当会造成并发冲突
  • tempdb 瓶颈：所有临时表都存储在 tempdb 中。高并发场景下 tempdb 可能成为性能瓶颈，需关注其文件配置和大小

07SELECT INTO 与 INSERT INTO SELECT

这两种语法都用于将查询结果插入表中，但有关键区别：

  • SELECT INTO：创建新表并插入数据（一步完成）。目标表不能预先存在
  • INSERT INTO SELECT：将查询结果插入已存在的表。目标表必须预先创建

脚本原文

-- SELECT INTO：创建临时表并填充数据
SELECT
    a.line_no,
    a.eqm_no,
    a.model_no,
    ROW_NUMBER() OVER (PARTITION BY a.line_no ORDER BY a.priority) AS rn
INTO #jt_moldinfo
FROM tb_eqm a WITH (NOLOCK)
WHERE a.status = 'A';

通用完整语法 通用扩展

INTO new_table
FROM source_table
WHERE ...;

-- 复制结构但不复制数据（加永假条件）
SELECT * INTO new_table FROM source_table WHERE 1=0;

-- 跨数据库复制

FROM SourceDB.dbo.source_table;

FROM source_table
WHERE ...;

SELECT col1, col2 FROM source_table;

风险提示：

  • SELECT INTO 不复制约束：主键、外键、默认值、索引都不会被复制。如果需要这些，必须用 CREATE TABLE 显式定义后 INSERT INTO SELECT
  • SELECT INTO 锁定：SELECT INTO 在某些情况下会对源表持有 Sch-S 锁，可能阻塞 DDL 操作
  • 列类型推导：SELECT INTO 根据源列推导新表列类型。表达式列的类型可能不符合预期，如 SUM(col) 可能推导为 DECIMAL 精度不够
  • INSERT 不指定列名：INSERT INTO tbl SELECT * 不安全——如果源表或目标表增删列，顺序可能不匹配。始终显式指定列名
  • 大批量插入：大量数据插入时考虑使用 BULK INSERT 或 BCP，性能远优于 INSERT INTO SELECT

08UPDATE ... FROM ... JOIN 语法

T-SQL 特有的 UPDATE ... FROM ... JOIN 语法允许在 UPDATE 语句中通过 JOIN 关联其他表来更新数据。这是 SQL Server 相对于标准 SQL 的扩展功能，在批量更新场景中非常实用。

脚本原文

UPDATE a
SET a.mold_count = ISNULL(b.total_count, 0),
    a.mold_limit = ISNULL(c.limit_val, 0)
FROM #jt_moldinfo a
    LEFT JOIN tb_eqm_config b WITH (NOLOCK)
        ON a.line_no = b.line_no
    LEFT JOIN tb_mold_rule c WITH (NOLOCK)
        ON a.line_no = c.line_no
WHERE a.status = 'A';

通用完整语法 通用扩展

-- 基本语法
UPDATE target_alias
SET target_alias.col1 = source_alias.col1,
    target_alias.col2 = expr
FROM target_table AS target_alias
    [INNER | LEFT | RIGHT | FULL] JOIN source_table AS source_alias
        ON join_condition
WHERE filter_condition;

-- 多表 JOIN 更新
UPDATE t
SET t.col1 = s1.val1,
    t.col2 = s2.val2
FROM target t
    INNER JOIN src1 s1 ON t.id = s1.id
    INNER JOIN src2 s2 ON t.id = s2.id;

-- 使用子查询更新
UPDATE t
SET t.status = 'done'
FROM target t
WHERE EXISTS (SELECT 1 FROM src s WHERE s.id = t.id);

固定写法 UPDATE FROM LEFT JOIN + ISNULL 安全更新模式

UPDATE a
SET a.target_col = ISNULL(b.source_col, a.target_col)  -- NULL 时保持原值
FROM #temp a
    LEFT JOIN source_table b WITH (NOLOCK)
        ON a.key_col = b.key_col;

UPDATE FROM JOIN 风险提示：

  • 多对一 JOIN 导致不确定更新：如果 JOIN 后每个目标行匹配多行源数据，SQL Server 的更新结果是不确定的（取最后一行）。应确保 JOIN 结果对每行目标数据唯一，或使用聚合
  • 忘记 WHERE 条件：UPDATE a SET a.col = ... FROM #temp a LEFT JOIN ... 如果没有 WHERE，会更新临时表所有行。虽然临时表数据有限，但生产表中这是灾难性的
  • 表别名混淆：UPDATE 后必须使用目标表的别名，不能直接用表名。如果写成 UPDATE target_table SET ... 而FROM 中用了别名，会报错
  • LEFT JOIN 产生 NULL：LEFT JOIN 不匹配时源列为 NULL。必须用 ISNULL() 处理，否则会将目标列更新为 NULL
  • 标准 SQL 不兼容：UPDATE FROM JOIN 是 T-SQL 扩展，MySQL、PostgreSQL、Oracle 语法不同。跨数据库迁移时需改写为 MERGE 或子查询
  • NOLOCK 在 UPDATE 中：被 UPDATE 的表不能加 NOLOCK（写操作需要锁）。只有 JOIN 的源表可以加 NOLOCK

09游标（CURSOR）

游标（Cursor）是一种逐行处理查询结果的机制。虽然 SQL 是面向集合的语言，推荐使用集合操作替代游标，但在需要逐行处理复杂逻辑（如调用存储过程、逐行发送消息）时，游标仍然不可替代。

游标类型：

类型说明性能
FORWARD_ONLY只能从第一行滚动到最后一行最快（默认）
FAST_FORWARD只进只读，启用性能优化推荐用于只读遍历
STATIC结果集快照存储在 tempdb较慢，但数据不随源表变化
KEYSET键集驱动，能感知新增/删除中等
DYNAMIC动态游标，实时反映源表变化最慢

脚本原文

-- 声明游标
DECLARE auto_mod_cur CURSOR FOR
SELECT line_no, eqm_no, model_no, mold_count, mold_limit
FROM #jt_moldinfo
WHERE rn = 1
  AND need_mold = 1;

-- 打开游标
OPEN auto_mod_cur;

-- 获取第一行
FETCH NEXT FROM auto_mod_cur INTO
    @line_no, @eqm_no, @model_no, @mold_count, @mold_limit;

-- 循环处理
WHILE @@FETCH_STATUS = 0
BEGIN
    -- 业务逻辑：检查型号数是否超过下限
    IF @mold_count > @mold_limit
    BEGIN
        DECLARE @msg VARCHAR(1000);
        SET @msg = FORMATMESSAGE(
            '自动点模失败。机台当前有任务型号数%s大于下限%s，本次不点模。',
            CAST(@mold_count AS VARCHAR(20)),
            CAST(@mold_limit AS VARCHAR(20))
        );
        RAISERROR(@msg, 16, 1);
    END

    -- 获取下一行（必须放在循环体最后）
    FETCH NEXT FROM auto_mod_cur INTO
        @line_no, @eqm_no, @model_no, @mold_count, @mold_limit;
END

-- 关闭并释放游标
CLOSE auto_mod_cur;
DEALLOCATE auto_mod_cur;

固定写法 游标完整生命周期模板（生产标准）

SELECT col1, col2 FROM #temp WHERE ...;

OPEN cur_name;
FETCH NEXT FROM cur_name INTO @v1, @v2;

WHILE @@FETCH_STATUS = 0
BEGIN
    -- 逐行处理逻辑

END

游标风险提示：

  • 忘记在循环末尾 FETCH：如果 WHILE 循环体内忘记 FETCH NEXT，@@FETCH_STATUS 永远为 0，导致无限循环。这是最常见的游标 Bug
  • 忘记 CLOSE/DEALLOCATE：游标不释放会占用服务器资源，导致内存泄漏。必须在 CATCH 块中也处理游标清理（如脚本 Step 2 所示）
  • CLOSE vs DEALLOCATE：CLOSE 关闭游标但保留定义，可以重新 OPEN。DEALLOCATE 完全释放游标资源。已关闭的游标只需 DEALLOCATE，已打开的游标需要先 CLOSE 再 DEALLOCATE
  • 性能问题：游标逐行处理比集合操作慢几个数量级。在可能的情况下，应优先考虑使用 WHILE + 临时表、窗口函数或 CASE WHEN 等集合方式替代
  • @@FETCH_STATUS 是全局的：如果嵌套游标，内层游标的 FETCH 会覆盖 @@FETCH_STATUS，导致外层循环判断出错。解决方案：内层游标使用独立变量保存状态，或避免嵌套游标
  • 游标在事务中：游标在事务中会持有锁。长时间运行的游标循环会阻塞其他会话。应尽量缩短游标的事务范围
  • LOCAL vs GLOBAL：默认行为由数据库设置决定。建议显式指定 LOCAL，避免游标泄漏到外层批处理

游标替代方案——使用 WHILE + IDENTITY 逐行处理：

-- 为临时表添加自增ID，用 WHILE 循环替代游标
DECLARE @i INT = 1, @max INT;
SELECT @max = MAX(id) FROM #temp;

WHILE @i <= @max
BEGIN
    SELECT @v1 = col1, @v2 = col2
    FROM #temp WHERE id = @i;

    -- 逐行处理

    SET @i = @i + 1;
END

10CASE 表达式

CASE 表达式是 SQL 中的条件表达式，类似于其他语言的 if-else 或 switch-case。它返回一个值，可以在 SELECT、UPDATE、ORDER BY、HAVING 等子句中使用。

两种形式：

  • 简单 CASE：CASE expr WHEN val1 THEN result1 WHEN val2 THEN result2 ELSE default END
  • 搜索 CASE：CASE WHEN cond1 THEN result1 WHEN cond2 THEN result2 ELSE default END

脚本原文

-- 在 SELECT 中使用 CASE 进行条件计算
SELECT
    a.line_no,
    CASE
        WHEN a.mold_count > a.mold_limit THEN '超过下限'
        WHEN a.mold_count = a.mold_limit THEN '刚好达到'
        ELSE '正常'
    END AS mold_status,
    CASE a.priority
        WHEN 1 THEN '高'
        WHEN 2 THEN '中'
        ELSE '低'
    END AS priority_desc
FROM #jt_moldinfo a;

通用完整语法 通用扩展

-- 1. 简单 CASE（等值匹配）
CASE input_expr
    WHEN val1 THEN result1
    WHEN val2 THEN result2
    [ ELSE default_result ]
END

-- 2. 搜索 CASE（条件判断，更灵活）
CASE
    WHEN cond1 THEN result1
    WHEN cond2 THEN result2
    [ ELSE default_result ]
END

-- 3. 在 UPDATE 中使用 CASE
UPDATE products
SET price = CASE
    WHEN category = 'A' THEN price * 1.1
    WHEN category = 'B' THEN price * 1.05
    ELSE price
END;

-- 4. 在 ORDER BY 中使用 CASE（动态排序）
SELECT * FROM orders
ORDER BY CASE @sort_col
    WHEN 'date' THEN order_date
    WHEN 'amount' THEN amount
END DESC;

-- 5. 在聚合中使用 CASE（条件计数）
SELECT
    SUM(CASE WHEN status = 'A' THEN 1 ELSE 0 END) AS active_count,
    SUM(CASE WHEN status = 'I' THEN 1 ELSE 0 END) AS inactive_count
FROM users;

CASE 表达式风险提示：

  • 忘记 ELSE 子句：如果所有 WHEN 都不匹配且没有 ELSE，CASE 返回 NULL。这可能导致意外结果，建议始终添加 ELSE
  • 简单 CASE 不支持范围：CASE col WHEN > 10 THEN ... 是错误的。简单 CASE 只支持等值匹配。范围判断必须用搜索 CASE
  • NULL 匹配问题：在简单 CASE 中，CASE NULL WHEN NULL THEN ... 不会匹配（NULL = NULL 结果为 UNKNOWN）。必须用搜索 CASE 的 CASE WHEN col IS NULL THEN ...
  • 结果类型一致性：所有 THEN/ELSE 分支的返回值类型必须兼容。SQL Server 会进行隐式转换，可能丢失精度
  • 短路与顺序：CASE 按 WHEN 顺序依次判断，第一个为 TRUE 的分支返回。后续分支不再评估。利用此特性可以简化嵌套条件

11窗口函数（OVER / PARTITION BY）完整列表

窗口函数（Window Functions）是 SQL Server 中最强大的分析功能之一。它们在一组行（"窗口"）上计算值，而不像聚合函数那样将多行合并为一行。每个行都保留并附带计算结果。

核心语法： 函数名() OVER ([PARTITION BY col1, col2] [ORDER BY col3] [ROWS/RANGE frame])

三大要素：

  • PARTITION BY：将数据分组，每个组独立计算窗口函数
  • ORDER BY：窗口内行的排序方向，影响排名类函数的结果
  • ROWS / RANGE：帧定义，控制窗口范围（如"当前行及前3行"）

脚本原文

-- 1. SUM() OVER (PARTITION BY ...)：分组累计求和
SELECT
    a.line_no,
    a.eqm_no,
    SUM(a.qty) OVER (PARTITION BY a.line_no) AS line_total,

-- 2. COUNT() OVER (PARTITION BY ...)：分组计数
    COUNT(*) OVER (PARTITION BY a.line_no) AS line_count,

-- 3. ROW_NUMBER() OVER (PARTITION BY ... ORDER BY ...)：分组排名
    ROW_NUMBER() OVER (
        PARTITION BY a.line_no
        ORDER BY a.priority DESC
    ) AS rn
FROM #jt_moldinfo a;

窗口帧（Frame）定义 通用扩展

-- ROWS 帧：按物理行数
SUM(qty) OVER (
    ORDER BY date
    ROWS BETWEEN 2 PRECEDING AND CURRENT ROW
)  -- 当前3行（前2行+当前行）的移动求和

-- RANGE 帧：按逻辑范围值
SUM(qty) OVER (
    ORDER BY date
    RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
)  -- 从第一行到当前行的累计求和（running total）

-- 帧定义关键字
-- UNBOUNDED PRECEDING：窗口起点（第一行）
-- UNBOUNDED FOLLOWING：窗口终点（最后一行）
-- CURRENT ROW：当前行
-- n PRECEDING：前 n 行
-- n FOLLOWING：后 n 行

固定写法 ROW_NUMBER 去重取每组第一条模式

-- 方法1：用 CTE + ROW_NUMBER 过滤
WITH ranked AS (
    SELECT *,
        ROW_NUMBER() OVER (
            PARTITION BY line_no ORDER BY priority DESC
        ) AS rn
    FROM #jt_moldinfo
)
SELECT * FROM ranked WHERE rn = 1;

-- 方法2：SELECT INTO 后再 WHERE 过滤（脚本中使用的方式）
SELECT ...,
    ROW_NUMBER() OVER (PARTITION BY line_no ORDER BY priority) AS rn
INTO #temp
FROM ...;

SELECT * FROM #temp WHERE rn = 1;

窗口函数风险提示：

  • LAST_VALUE 陷阱：LAST_VALUE() 不加帧定义时，默认帧为 RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW，即"第一行到当前行"。取每组最后一条需要显式指定 ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING
  • 性能问题：窗口函数需要排序（ORDER BY），大数据量时可能产生 Sort 运算符。确保 PARTITION BY 和 ORDER BY 列有索引
  • ROW_NUMBER 不能在 WHERE 中使用：窗口函数只能在 SELECT 和 ORDER BY 中使用，不能直接在 WHERE/HAVING 中过滤。需要通过 CTE 或子查询包装后再过滤
  • NULL 值排序：在 ORDER BY 中，NULL 默认排在最前面（ASC）或最后面（DESC）。使用 CASE WHEN col IS NULL THEN 1 ELSE 0 END 控制 NULL 位置
  • 聚合函数 OVER 不加 ORDER BY：如果不加 ORDER BY，聚合函数对整个分区计算同一值。加上 ORDER BY 后变为累计/滑动聚合，语义完全不同

12子查询与 EXISTS / IN

子查询是嵌套在另一个查询中的查询。根据返回结果可分为：

  • 标量子查询：返回单个值，可用于 SELECT、WHERE 等
  • 多值子查询：返回一列多行，常与 IN/ANY/ALL 配合
  • 表子查询：返回多列多行，常用于 FROM 子句（派生表）
  • 相关子查询：引用外层查询的列，每行执行一次
  • EXISTS 子查询：只判断是否存在行，不返回具体值

脚本原文

SELECT a.*
FROM #jt_moldinfo a
WHERE EXISTS (
    SELECT 1
    FROM tb_task b WITH (NOLOCK)
        INNER JOIN tb_task_detail c WITH (NOLOCK)
            ON b.task_id = c.task_id
    WHERE b.line_no = a.line_no
      AND b.status = 'A'
);

  • DATEDIFF 边界问题：DATEDIFF(HOUR, '2026-01-01 01:59:59', '2026-01-01 02:00:01') 返回 1，虽然实际只差 2 秒！DATEDIFF 计算的是"跨越了几个边界"，不是精确差值

  • 时区问题：GETDATE 返回服务器本地时间。如果服务器在不同时区，建议使用 SYSUTCDATETIME() 存 UTC，查询时转换
  • 日期字符串格式：始终使用 YYYYMMDD 或 YYYY-MM-DDTHH:MM:SS 格式以避免区域设置歧义。'2026-08-07' 在某些设置下可能被解析为 2月7日
  • 1900-01-01 基准：DATEDIFF(HOUR, 0, GETDATE()) 中的 0 代表 1900-01-01 00:00:00。这是 SQL Server DATETIME 的内部基准日期

15NULL 处理与三值逻辑 核心重点

NULL 是 SQL 中最容易被误解的概念之一。NULL 不等于 0、不等于空字符串、不等于"没有值"。NULL 表示"未知值"（Unknown）或"不适用"（Not Applicable）。理解 NULL 的行为是写出正确 SQL 的关键。

SQL 使用三值逻辑（Three-Valued Logic, 3VL），逻辑表达式的结果有三个可能值：TRUE、FALSE、UNKNOWN。

脚本原文

-- ISNULL 贯穿整个脚本的使用
ISNULL(a.mold_count, 0)         -- NULL 替换为 0
ISNULL(b.total_count, 0)      -- LEFT JOIN 不匹配时替换为 0
ISNULL(@recipient, '')       -- NULL 替换为空字符串

一、三值逻辑详解

在 SQL 中，任何包含 NULL 的比较运算结果都是 UNKNOWN，而非 TRUE 或 FALSE。WHERE 子句只接受 TRUE，UNKNOWN 和 FALSE 一样被过滤掉。

三值逻辑的关键结论：

  • NOT (UNKNOWN) = UNKNOWN，不是 TRUE！
  • UNKNOWN AND TRUE = UNKNOWN
  • UNKNOWN OR TRUE = TRUE（OR 中有一个 TRUE 即为 TRUE）
  • UNKNOWN AND FALSE = FALSE（AND 中有一个 FALSE 即为 FALSE）
  • WHERE 子句只保留 TRUE 的行，UNKNOWN 被过滤

二、NULL 在比较中的行为

-- 场景：查找 status 不等于 'A' 的行
SELECT * FROM orders WHERE status <> 'A';
-- 如果某行 status 为 NULL，该行不会被返回！
-- 因为 NULL <> 'A' 的结果是 UNKNOWN，被 WHERE 过滤

-- 正确写法：显式包含 NULL
SELECT * FROM orders WHERE status <> 'A' OR status IS NULL;
-- 或
SELECT * FROM orders WHERE ISNULL(status, '') <> 'A';

IS NULL vs = NULL（高频错误）

-- 错误写法：永远返回 0 行
SELECT * FROM orders WHERE status = NULL;
-- 因为 NULL = NULL 结果是 UNKNOWN，WHERE 只接受 TRUE

-- 正确写法
SELECT * FROM orders WHERE status IS NULL;

-- 例外：SET ANSI_NULLS OFF 时 = NULL 可以工作
-- 但强烈不推荐！ANSI_NULLS OFF 已被废弃

三、NULL 在聚合函数中的行为

聚合函数（SUM、AVG、COUNT、MIN、MAX）自动忽略 NULL 值，但 COUNT(*) 例外。

-- 假设表数据：
-- id | price
-- ---|------
--  1 |  100
--  2 | NULL
--  3 |  200

SELECT
    COUNT(*) AS cnt_all,         -- 3（计算所有行，包括 NULL）
    COUNT(price) AS cnt_price,    -- 2（忽略 NULL）
    SUM(price) AS sum_price,      -- 300（忽略 NULL，不是 NULL）
    AVG(price) AS avg_price,      -- 150（300/2，不是 300/3！）
    MIN(price) AS min_price,      -- 100
    MAX(price) AS max_price       -- 200
FROM products;

-- 如果所有行都是 NULL：
-- COUNT(price) = 0
-- SUM(price) = NULL（不是 0！）
-- AVG(price) = NULL
-- MIN/MAX(price) = NULL

聚合函数 NULL 风险：

  • AVG 计算陷阱：AVG(price) 忽略 NULL 行后计算平均值。如果 3 行中 1 行为 NULL，AVG = SUM/COUNT(非NULL) = 300/2 = 150，而非 300/3 = 100。如果业务需要将 NULL 视为 0，必须 AVG(ISNULL(price, 0))
  • SUM 全 NULL 返回 NULL：如果所有行都是 NULL，SUM 返回 NULL 而非 0。脚本中用 ISNULL(SUM(col), 0) 处理
  • COUNT(*) vs COUNT(col)：COUNT(*) 计算所有行（含全 NULL 行），COUNT(col) 只计算 col 非 NULL 的行。混用会导致统计错误
  • GROUP BY 中的 NULL：GROUP BY 将所有 NULL 值分到同一组。NULL 被视为"相等"进行分组
  • DISTINCT 中的 NULL：DISTINCT 将所有 NULL 视为相同值，只保留一个
  • ORDER BY 中的 NULL：默认 ASC 时 NULL 排在最前，DESC 时排在最后。可通过 CASE 控制位置

四、NULL 在字符串拼接中的行为

-- 默认行为（SET CONCAT_NULL_YIELDS_NULL ON）：
SELECT 'Hello' + NULL;          -- 结果: NULL
SELECT 'Hello' + NULL + 'World';  -- 结果: NULL

-- 任何字符串 + NULL = NULL（除非改变设置）

-- 解决方案1：ISNULL 替换
SELECT 'Hello ' + ISNULL(name, 'Unknown');

-- 解决方案2：CONCAT 函数（自动将 NULL 转为空串）
SELECT CONCAT('Hello ', NULL, 'World');  -- 结果: 'Hello World'

-- 解决方案3：CONCAT_WS（跳过 NULL，用分隔符连接）
SELECT CONCAT_WS(', ', 'Alice', NULL, 'Bob');  -- 结果: 'Alice, Bob'

-- 解决方案4：SET CONCAT_NULL_YIELDS_NULL OFF（不推荐）
SET CONCAT_NULL_YIELDS_NULL OFF;
SELECT 'Hello ' + NULL;  -- 结果: 'Hello '
-- 此设置已废弃，不应在生产中使用

七、NOT IN NULL 陷阱（最重要的 NULL 陷阱）

NOT IN 与 NULL 的致命陷阱

-- 子查询结果包含 NULL 时
SELECT * FROM orders
WHERE cust_id NOT IN (
    SELECT cust_id FROM blacklist
);

-- 等价于：
-- WHERE cust_id <> val1 AND cust_id <> val2 AND ... AND cust_id <> NULL
-- 最后一个 AND cust_id <> NULL 的结果是 UNKNOWN
-- TRUE AND ... AND UNKNOWN = UNKNOWN
-- UNKNOWN 被 WHERE 过滤 → 整个查询返回 0 行！

-- 即使 blacklist 中只有一行 cust_id 为 NULL，所有行都会被过滤

-- 正确做法：
-- 方案1：NOT EXISTS（推荐）
SELECT * FROM orders o
WHERE NOT EXISTS (
    SELECT 1 FROM blacklist b
    WHERE b.cust_id = o.cust_id
);

-- 方案2：子查询中排除 NULL
SELECT * FROM orders
WHERE cust_id NOT IN (
    SELECT cust_id FROM blacklist WHERE cust_id IS NOT NULL
);

-- 方案3：LEFT JOIN + IS NULL
SELECT o.*
FROM orders o
    LEFT JOIN blacklist b ON o.cust_id = b.cust_id
WHERE b.cust_id IS NULL;

FORMATMESSAGE 风险提示 风险提示

  • %s 参数必须为字符串类型：脚本中使用 CAST(@机台总型号数 AS VARCHAR(20)) 将 INT 转为 VARCHAR 后传给 %s。如果不转换直接传 INT 给 %s，会报错"参数类型冲突"。这是最常见的 FORMATMESSAGE 错误。替代方案是使用 %d 占位符直接传整数
  • 参数数量必须匹配：占位符数量必须与参数数量一致。多出的参数被忽略，少了会报错
  • NULL 参数：如果参数为 NULL，%s 会输出空串，%d 会输出 0。这可能不是期望行为。应先用 ISNULL 处理
  • 返回类型为 NVARCHAR：FORMATMESSAGE 返回 NVARCHAR，赋值给 VARCHAR 变量时如果包含 Unicode 字符可能丢失
  • 内联字符串需要 SQL Server 2016+：SQL Server 2014 及以下不支持直接传字符串模板，必须先通过 sp_addmessage 创建消息再用 msg_id 引用
  • 消息长度限制：sys.messages 中的消息文本最大 2047 字符。FORMATMESSAGE 返回值最大为 2047 字符（NVARCHAR）
  • % 转义：消息中的 % 需要用 %% 转义，否则会被解析为占位符
  • 参数顺序：参数按位置匹配占位符，不能通过名称引用。建议使用清晰的占位符顺序

17EXEC 与动态 SQL

动态 SQL是在运行时构造和执行的 SQL 语句。当表名、列名、查询条件等需要在运行时确定时，必须使用动态 SQL。

两种执行方式：

  • EXEC()：简单但不支持参数化，存在 SQL 注入风险
  • sp_executesql：支持参数化，可重用执行计划，安全

脚本原文

-- 跨数据库调用存储过程
EXEC zgRdp.dbo.p_sys_call_make_msg
    @MsgTile = @remark1,
    @Body = @rem_20,
    ...;

通用完整语法 通用扩展

-- 1. EXEC 执行存储过程
EXEC dbo.p_procedure @param = 1;
EXEC zgRdp.dbo.p_procedure @param = 1;  -- 跨数据库

-- 2. EXEC() 执行动态 SQL 字符串
DECLARE @sql VARCHAR(1000);
SET @sql = 'SELECT * FROM ' + @table_name;
EXEC(@sql);

-- 3. sp_executesql（推荐：支持参数化）
DECLARE @sql NVARCHAR(1000);
SET @sql = N'SELECT * FROM users WHERE id = @id';
EXEC sp_executesql
    @sql,
    N'@id INT',
    @id = 123;

-- 4. sp_executesql 带输出参数
DECLARE @count INT;
EXEC sp_executesql
    N'SELECT @cnt = COUNT(*) FROM users WHERE status = @st',
    N'@st VARCHAR(10), @cnt INT OUTPUT',
    @st = 'A',
    @cnt = @count OUTPUT;

-- 5. 动态表名查询
DECLARE @table NVARCHAR(128) = 'orders_202608';
DECLARE @sql NVARCHAR(1000);
SET @sql = FORMATMESSAGE('SELECT * FROM %s WHERE date >= @dt', @table);
EXEC sp_executesql @sql, N'@dt DATE', @dt = '2026-08-01';

动态 SQL 风险提示：

  • SQL 注入：直接拼接用户输入到 SQL 字符串中是最大的安全风险。永远不要 'SELECT * FROM ' + @user_input。使用 sp_executesql 参数化或 QUOTENAME() 处理标识符
  • QUOTENAME 保护标识符：QUOTENAME(@table_name) 会将表名包裹在 [] 中，防止注入。如 QUOTENAME('users; DROP TABLE orders') → [users; DROP TABLE orders]（安全的表名引用）
  • 作用域问题：动态 SQL 在单独的作用域中执行。动态 SQL 中创建的临时表、变量在动态 SQL 执行后不可见。反之亦然
  • NVARCHAR 要求：sp_executesql 的 SQL 字符串必须是 NVARCHAR。VARCHAR 会报错
  • 长度限制：EXEC() 和 sp_executesql 的字符串参数有长度限制（NVARCHAR(MAX) 可突破）
  • 权限上下文：动态 SQL 默认在调用者权限下执行。如需在所有者权限下执行，使用 EXECUTE AS 或签名存储过程

固定写法 安全的动态 SQL 模板

DECLARE @sql NVARCHAR(1000);

-- 使用 QUOTENAME 保护表名

           N' WHERE status = @st AND date >= @dt';

-- 使用 sp_executesql 参数化
EXEC sp_executesql
    @sql,
    N'@st VARCHAR(10), @dt DATE',
    @st = 'A',
    @dt = '2026-08-01';

18WITH (NOLOCK) 与隔离级别

WITH (NOLOCK) 是表级提示，相当于 READ UNCOMMITTED 隔离级别。它允许读取未提交的数据（脏读），但不会对被读取的表加共享锁，因此不会阻塞其他事务的写操作。

事务隔离级别（从低到高）：

隔离级别脏读不可重复读幻读说明
READ UNCOMMITTED可能可能可能最低隔离，等同于 NOLOCK
READ COMMITTED（默认）不可能可能可能只读取已提交数据
REPEATABLE READ不可能不可能可能锁定读取行直到事务结束
SNAPSHOT不可能不可能不可能行版本控制，读取快照
SERIALIZABLE不可能不可能不可能最高隔离，锁定范围

脚本原文

SELECT a.line_no, a.eqm_no
FROM zgDmp.dbo.tb_bas_eqm_line a WITH (NOLOCK)
WHERE a.status = 'A';

SELECT @recipient = STRING_AGG(b.emp_no, ',')
FROM tb_mes_msg_type a WITH (NOLOCK)
    LEFT JOIN tb_mes_msg_type_users b WITH (NOLOCK)
        ON a.msg_type_code = b.msg_type_code;

通用完整语法 通用扩展

-- 1. 表级 NOLOCK 提示
SELECT * FROM orders WITH (NOLOCK);

-- 2. 多表 NOLOCK
SELECT *
FROM orders a WITH (NOLOCK)
    INNER JOIN customers b WITH (NOLOCK) ON a.cust_id = b.id;

-- 3. 会话级隔离级别设置
SET TRANSACTION ISOLATION LEVEL READ UNCOMMITTED;
SELECT * FROM orders;  -- 无需每表加 NOLOCK
SET TRANSACTION ISOLATION LEVEL READ COMMITTED;  -- 恢复默认

-- 4. 其他常用表提示
SELECT * FROM orders WITH (READPAST);      -- 跳过被锁的行
SELECT * FROM orders WITH (UPDLOCK);      -- 读取时加更新锁
SELECT * FROM orders WITH (ROWLOCK);      -- 使用行级锁
SELECT * FROM orders WITH (NOLOCK, READPAST); -- 组合提示

NOLOCK 风险提示 风险提示

  • 脏读：NOLOCK 会读取未提交的数据。如果另一个事务正在修改但尚未提交（可能回滚），你读到的是"脏数据"。对财务、库存等关键数据，绝对不能使用 NOLOCK
  • 不可重复读：同一查询两次执行结果可能不同，因为其他事务在期间修改了数据
  • 幻读：行数可能变化，因为其他事务插入/删除了行
  • 读取不一致：在大表扫描中，如果数据页被其他事务重新组织，可能读到重复行或丢失行。这是 NOLOCK 最危险的副作用
  • 适用场景：NOLOCK 适合报表查询、数据分析等对数据精度要求不高的场景。生产交易系统应使用 READ COMMITTED 或 SNAPSHOT
  • 更好的替代方案：READ_COMMITTED_SNAPSHOT 数据库选项启用后，READ COMMITTED 使用行版本控制（类似 SNAPSHOT），读取不阻塞写入，也不脏读。这是比 NOLOCK 更安全的选择：ALTER DATABASE db SET READ_COMMITTED_SNAPSHOT ON
  • 脚本中的使用：自动点模脚本在所有表读取时使用 NOLOCK，这是 MES 系统的常见做法——为了减少锁争用，接受脏读风险。但在更新临时表时不需要 NOLOCK（临时表是会话私有的）

固定写法 NOLOCK 标准使用模式

-- 每个源表都加 WITH (NOLOCK)
SELECT a.col1, b.col2
FROM table_a a WITH (NOLOCK)
    INNER JOIN table_b b WITH (NOLOCK)
        ON a.id = b.a_id
    LEFT JOIN table_c c WITH (NOLOCK)
        ON a.code = c.code
WHERE a.status = 'A';

-- 或者设置会话级隔离级别（等价于所有表加 NOLOCK）
SET TRANSACTION ISOLATION LEVEL READ UNCOMMITTED;

跨数据库查询风险提示：

  • 权限要求：跨数据库查询需要在目标数据库中有相应权限。可通过跨数据库链（DB chaining）或模拟（Impersonation）管理
  • 性能影响：跨数据库查询可能产生额外的锁和资源开销。特别是链接服务器查询，网络延迟是主要瓶颈
  • 同义词优势：使用同义词后，如果目标数据库改名或迁移，只需修改同义词定义，无需修改所有引用代码
  • 链接服务器性能：链接服务器查询可能将大量数据拉到本地处理。使用 OPENQUERY 让查询在远程执行，只返回结果
  • 分布式事务：跨实例操作涉及分布式事务（MSDTC），配置复杂且性能较差。尽量在单实例内完成
  • 数据库迁移：大量跨数据库引用会增加数据库迁移难度。建议使用同义词解耦

系统函数风险提示：

  • @@IDENTITY vs SCOPE_IDENTITY()：@@IDENTITY 返回当前会话任何作用域的最后 IDENTITY 值，包括触发器中插入的。SCOPE_IDENTITY() 只返回当前作用域的。生产环境必须使用 SCOPE_IDENTITY() 避免触发器干扰
  • @@ERROR 时效性：@@ERROR 只在每条语句执行后有效，下一条语句会覆盖它。如果要检查多个语句的错误，必须每条后立即检查。推荐使用 TRY/CATCH 替代
  • @@ROWCOUNT 被覆盖：@@ROWCOUNT 在任何语句后都会被重置。如果先 SELECT 再 IF，IF 语句会把 @@ROWCOUNT 重置为 0。应先保存到变量
  • OBJECT_ID 与临时表：OBJECT_ID('tempdb..#temp') 检查临时表是否存在。但不同会话的临时表名相同（如 #temp），OBJECT_ID 在 tempdb 中查找可能匹配到其他会话的同名表。实际上临时表在 tempdb 中有内部唯一名，OBJECT_ID 能正确匹配当前会话的

21类型转换 CAST / CONVERT / TRY_CONVERT

SQL Server 提供多种类型转换函数：

  • CAST：ANSI SQL 标准转换，语法简洁
  • CONVERT：T-SQL 扩展，支持日期/数字格式化
  • TRY_CAST / TRY_CONVERT：转换失败返回 NULL 而非报错
  • PARSE / TRY_PARSE：基于 .NET 的解析，支持区域性

脚本原文

-- 将 INT 转为 VARCHAR 用于 FORMATMESSAGE 参数
CAST(@机台总型号数 AS VARCHAR(20))
CAST(@机台点模下限 AS VARCHAR(20))

通用完整语法 通用扩展

-- 1. CAST：标准语法
CAST(expression AS data_type [(length)])

-- 2. CONVERT：T-SQL 扩展，支持样式码
CONVERT(data_type [(length)], expression [, style])

-- 3. TRY_CAST / TRY_CONVERT：转换失败返回 NULL
TRY_CAST(expression AS data_type)
TRY_CONVERT(data_type, expression [, style])

-- 4. PARSE / TRY_PARSE：.NET 解析
PARSE(string AS data_type [USING culture])
TRY_PARSE(string AS data_type [USING culture])

常用转换示例

-- 日期转字符串

CONVERT(VARCHAR(19), GETDATE(), 120)              -- '2026-08-07 14:30:15'
CONVERT(VARCHAR(8), GETDATE(), 112)               -- '20260807'

类型转换风险提示：

  • 转换失败报错：CAST('abc' AS INT) 会抛出错误，中断批处理。如果不确定转换是否成功，使用 TRY_CAST 或 TRY_CONVERT
  • 隐式转换性能：SQL Server 会自动进行隐式类型转换（如 VARCHAR 列与 NVARCHAR 参数比较），但这可能导致索引失效（全表扫描）。确保比较双方类型一致
  • 截断 vs 四舍五入：CAST(123.9 AS INT) = 123（截断），CAST(123.9 AS DECIMAL(10,0)) = 124（四舍五入）。行为不同，需注意
  • VARCHAR 长度省略：CAST(@v AS VARCHAR) 不指定长度时，默认长度为 30（在 CAST 中）或 1（在变量声明中）。始终显式指定长度
  • 日期格式歧义：'06/07/2026' 在 US 英语中是 6月7日，在英式中是 7月6日。使用样式码 112（yyyymmdd）或 120 避免歧义
  • NVARCHAR 转换：处理 Unicode 字符串时使用 NVARCHAR/NCHAR，避免中文乱码
  • FORMATMESSAGE 参数类型：脚本中 CAST(@机台总型号数 AS VARCHAR(20)) 是为了将 INT 传给 FORMATMESSAGE 的 %s 占位符。也可以直接用 %d 占位符传 INT，但 %s + CAST 是更通用的模式

固定写法 安全类型转换模式

-- 1. 安全字符串转数值（使用 TRY_CAST）
DECLARE @val INT;
SET @val = ISNULL(TRY_CAST(@input AS INT), 0);

-- 2. 安全日期转换
DECLARE @date DATE;
SET @date = ISNULL(TRY_CONVERT(DATE, @input, 120), GETDATE());

-- 3. FORMATMESSAGE 参数转换
FORMATMESSAGE(
    '值: %s',
    CAST(ISNULL(@num, 0) AS VARCHAR(20))
)

-- 4. 标准日期格式化
CONVERT(VARCHAR(19), GETDATE(), 120)  -- '2026-08-07 14:30:15'

五步结构概览

设计原则：

  • 错误兜底：全部包在 BEGIN TRY ... BEGIN CATCH 中
  • 游标安全：CATCH 块中检查 CURSOR_STATUS 并关闭/释放游标
  • 临时表安全：创建前 IF OBJECT_ID 判断，结束后 DROP TABLE
  • NOLOCK 一致：所有表读取加 WITH (NOLOCK)
  • NULL 防御：所有可能为 NULL 的字段用 ISNULL 包裹

完整 DEMO 模板代码

/* ================================================================
   存储过程模板：5 步标准结构
   基于 p_mold_auto_apply_v4_bak 抽象
   适用场景：批量数据处理 + 逐行逻辑 + 错误通知
   ================================================================ */
CREATE PROCEDURE dbo.p_template_demo
    @is_auto INT = 0        -- 0=人工触发, 1=自动触发
AS
BEGIN
    SET NOCOUNT ON;

    /* ================================================================
       全局变量声明
       ================================================================ */
    DECLARE @err_msg VARCHAR(5000);
    DECLARE @recipient VARCHAR(2000);
    DECLARE @send_id VARCHAR(50) = NEWID();

    /* ================================================================
       BEGIN TRY + BEGIN TRANSACTION  (固定写法)
       ================================================================ */
    BEGIN TRY
        BEGIN TRANSACTION;

        /* ============================================================
           Step 1: 参数校验与前置检查
           ============================================================ */

        /* 1.1 时间窗口校验 (仅人工触发时检查) */
        IF @is_auto = 0
        BEGIN
            DECLARE @curr_hour INT = DATEPART(HOUR, GETDATE());
            IF (@curr_hour BETWEEN 3 AND 6)
               OR (@curr_hour BETWEEN 15 AND 18)
            BEGIN
                RAISERROR('3点-6点、15点-18点期间不允许人工触发!', 16, 1);
            END
        END

        /* 1.2 业务前置条件检查 */
        IF NOT EXISTS (
            SELECT 1
            FROM dbo.tb_config WITH (NOLOCK)
            WHERE config_code = 'ENABLED'
        )
        BEGIN
            RAISERROR('系统未启用，无法执行', 16, 1);
        END

        /* ============================================================
           Step 2: 临时表构建
           ============================================================ */

        /* 2.1 安全删除旧临时表 (固定写法) */
        IF OBJECT_ID('tempdb..#jt_data') IS NOT NULL
            DROP TABLE #jt_data;

        /* 2.2 SELECT INTO 创建临时表 */
        SELECT
            a.sheet_no,
            a.eqm_code,
            a.status,
            ISNULL(a.priority, 0) AS priority,
            ROW_NUMBER() OVER (PARTITION BY a.eqm_code ORDER BY a.create_time DESC) AS rn,
            SUM(a.qty) OVER (PARTITION BY a.eqm_code) AS total_qty,
            CAST(NULL AS VARCHAR(100)) AS result_msg
        INTO #jt_data
        FROM dbo.tb_main a WITH (NOLOCK)
        WHERE a.status IN ('1', '2')
          AND a.create_time >= DATEADD(HOUR, -5, GETDATE());

        /* 2.3 创建索引加速后续 JOIN */
        CREATE NONCLUSTERED INDEX ix_jt_data_eqm ON #jt_data(eqm_code);

        /* ============================================================
           Step 3: 更新计算 (UPDATE ... FROM ... JOIN)
           ============================================================ */

        /* 3.1 关联补充字段 */
        UPDATE t
        SET
            t.eqm_name    = ISNULL(b.eqm_name, ''),
            t.dept_name   = ISNULL(c.dept_name, '未分配'),
            t.limit_value = ISNULL(d.limit_value, 0)
        FROM #jt_data t
            LEFT JOIN dbo.tb_eqm b WITH (NOLOCK)
                ON t.eqm_code = b.eqm_code
            LEFT JOIN zgDmp.dbo.tb_hr_employee c WITH (NOLOCK)
                ON b.emp_no = c.emp_no
            LEFT JOIN dbo.tb_config d WITH (NOLOCK)
                ON d.config_code = t.eqm_code;

        /* 3.2 CASE 表达式标记状态 */
        UPDATE #jt_data
        SET result_msg = CASE
            WHEN total_qty > limit_value THEN '超限'
            WHEN total_qty = 0 THEN '无数据'
            ELSE '正常'
        END;

        /* ============================================================
           Step 4: 游标循环处理
           ============================================================ */

        /* 4.1 游标变量声明 */
        DECLARE
            @cur_sheet_no VARCHAR(50),
            @cur_eqm_code VARCHAR(50),
            @cur_total    INT,
            @cur_limit    INT;

        /* 4.2 声明游标 */
        DECLARE proc_cur CURSOR FOR
        SELECT sheet_no, eqm_code, total_qty, limit_value
        FROM #jt_data
        WHERE rn = 1
          AND result_msg = '超限';

        /* 4.3 打开游标并取首行 */
        OPEN proc_cur;
        FETCH NEXT FROM proc_cur INTO
            @cur_sheet_no, @cur_eqm_code, @cur_total, @cur_limit;

        /* 4.4 循环处理 */
        WHILE @@FETCH_STATUS = 0
        BEGIN
            /* 4.4.1 业务逻辑处理 */
            IF @cur_total > @cur_limit
            BEGIN
                /* 使用 FORMATMESSAGE 生成错误消息 */
                RAISERROR(
                    FORMATMESSAGE(
                        '处理失败。机台%s当前数量%d大于下限%d，跳过。',
                        CAST(@cur_eqm_code AS VARCHAR(20)),
                        CAST(@cur_total AS VARCHAR(20)),
                        CAST(@cur_limit AS VARCHAR(20))
                    ),
                    16, 1
                );

                /* CONTINUE 跳过当前行 */
                CONTINUE;
            END

            /* 4.4.2 更新业务表 */
            UPDATE dbo.tb_main
            SET status = '5',
                update_time = GETDATE()
            WHERE sheet_no = @cur_sheet_no;

            /* 4.4.3 取下一行 (固定写法, 必须在循环末尾) */
            FETCH NEXT FROM proc_cur INTO
                @cur_sheet_no, @cur_eqm_code, @cur_total, @cur_limit;
        END

        /* 4.5 关闭并释放游标 (固定写法) */
        CLOSE proc_cur;
        DEALLOCATE proc_cur;

        /* ============================================================
           Step 5: 后处理与通知
           ============================================================ */

        /* 5.1 提交事务 */
        COMMIT TRANSACTION;

        /* 5.2 清理临时表 */
        IF OBJECT_ID('tempdb..#jt_data') IS NOT NULL
            DROP TABLE #jt_data;

        /* 5.3 记录执行日志 */
        INSERT INTO dbo.tb_proc_log(proc_name, execute_time, status)
        VALUES('p_template_demo', GETDATE(), '成功');

    END TRY
    BEGIN CATCH
        /* ============================================================
           CATCH 块: 错误处理 6 步法 (固定写法, 必须与原脚本一致)
           ============================================================ */

        /* Step 1: 回滚事务 */
        IF @@TRANCOUNT > 0
            ROLLBACK TRANSACTION;

        /* Step 2: 关闭游标 (如果仍然打开) */
        IF CURSOR_STATUS('global', 'proc_cur') <> -3
           OR CURSOR_STATUS('local', 'proc_cur') <> -3
        BEGIN
            CLOSE proc_cur;
            DEALLOCATE proc_cur;
        END;

        /* Step 3: 调用系统错误记录过程 */
        EXEC dbo.p_sys_raiserror;

        /* Step 4: 声明变量并获取错误信息 */
        DECLARE
            @remark1   VARCHAR(2000),
            @rem_20    VARCHAR(5000),
            @body      VARCHAR(MAX);

        SELECT @remark1 = '处理出错';
        SELECT @body    = '处理出错';
        SELECT @rem_20  = ERROR_MESSAGE();  -- 获取错误消息

        /* Step 5: 查询通知接收人 (STRING_AGG) */
        SELECT @recipient = STRING_AGG(b.emp_no, ',')
        FROM dbo.tb_mes_msg_type a
            LEFT JOIN dbo.tb_mes_msg_type_users b
                ON a.msg_type_code = b.msg_type_code
        WHERE a.msg_type_code = 'MJTBCC';

        /* Step 6: 发送多通道通知 (微信/PC/Android) */
        EXEC zgRdp.dbo.p_sys_call_make_msg
            @MsgTile      = @remark1,
            @MsgType       = 0,
            @Body          = @rem_20,         -- 使用 ERROR_MESSAGE() 结果
            @SheetNo       = '',
            @LevelId       = 0,
            @WeixinPush    = 1,
            @PcPush        = 1,
            @AndroidPush   = 1,
            @SendUser      = '',
            @RecUsers      = @recipient,
            @RecRole       = '',
            @RecSql        = '',
            @MenuId        = '',
            @temp_id       = 'DxOjZaab_bWL6mwzjVLq5bWXnFycR35MH2DwQAgJimQ',
            @define1       = '',
            @define2       = '',
            @define3       = '',
            @define4       = '',
            @define5       = '',
            @extend_field  = '';
    END CATCH;
END

使用建议

最佳实践 何时使用此模板

  • 批量 + 逐行混合处理：先用 SELECT INTO + UPDATE FROM JOIN 批量处理大部分数据，再用游标处理需要复杂逐行逻辑的记录
  • 需要错误通知：CATCH 块内置了完整的多通道通知机制，适合生产环境关键存储过程
  • 需要事务保护：多表更新操作需要原子性保证的场景

风险提示 模板使用注意事项

  • 游标性能：游标是性能杀手，能用集合操作（UPDATE FROM JOIN）完成的就不要用游标。仅在确实需要逐行条件判断和复杂分支时使用
  • 事务范围：事务应尽量短，避免长时间锁定。不要在游标循环内开启新事务（嵌套事务在 SQL Server 中行为复杂）
  • NOLOCK 一致性：WITH(NOLOCK) 允许脏读，适合报表/查询场景。对需要事务一致性的写入前查询，不要使用 NOLOCK
  • 临时表 vs 表变量：大数据量（>10000行）用临时表（有统计信息，优化器能优化）；小数据量用表变量（无统计信息，但开销小）
  • STRING_AGG 兼容性：SQL Server 2017+ 才支持 STRING_AGG。旧版本用 STUFF(... FOR XML PATH('')) 替代
  • FORMATMESSAGE 参数数限制：FORMATMESSAGE 最多支持 20 个参数占位符（%s / %d / %i 等）
  • CURSOR_STATUS 检查：CATCH 块中检查游标状态时，必须同时检查 'global' 和 'local' 两种作用域，否则可能遗漏
  • NEWID() 默认值：DECLARE @send_id VARCHAR(50) = NEWID() 是在声明时赋默认值，仅 SQL Server 2008+ 支持

总结： 本模板的核心价值在于将复杂存储过程拆分为清晰的 5 步结构，并在 CATCH 块中内置了生产级的错误处理和通知机制。通过固定 Step 1 ~ Step 5 + CATCH 6 步法的结构，可以确保存储过程的健壮性、可维护性和可追溯性。
