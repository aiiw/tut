一、存储过程基础

存储过程是一组预编译的 SQL 语句，可以接收参数、返回结果。这是 SQL Server 最常用的编程对象之一。

1.1 创建语法

CREATE PROCEDURE [dbo].[sp_mold_test_task_query] @org_no VARCHAR(20) = '003', @query_type CHAR(1) = '1', @trial_date_checked BIT = 0, @mold_no VARCHAR(50) = '' AS BEGIN SET NOCOUNT ON; -- 业务逻辑写在这里 END

要点：

  • 参数定义：参数名以 @ 开头，可以设置默认值。调用时不传就用默认值。
  • SET NOCOUNT ON：禁止返回"影响行数"消息，减少网络开销，是存储过程的标准写法。
  • BEGIN...END：代码块的边界，类似其他语言的花括号 { }。

1.2 调用方式

-- 完整调用（指定参数名，推荐） EXEC dbo.sp_mold_test_task_query @org_no = '003', @query_type = '1', @mold_no = '100X44X1.8-2012'; -- 简写（按参数顺序传） EXEC dbo.sp_mold_test_task_query '003', '1';

二、存储过程的输入输出参数

存储过程的参数不仅可以"传入"，还可以"传出"。本脚本用的都是输入参数，这里系统讲一下参数的几种类型。

2.1 输入参数（默认）

默认情况下，参数都是输入参数，调用时把值传进去。

CREATE PROCEDURE dbo.sp_demo @mold_no VARCHAR(50) = '' -- 输入参数，有默认值 AS BEGIN SELECT * FROM tb_bas_mold WHERE mold_no = @mold_no END

2.2 输出参数（OUTPUT）

在参数后面加 OUTPUT 关键字，就是输出参数。存储过程内部给它赋值，调用者能拿到这个值。

CREATE PROCEDURE dbo.sp_get_mold_count @prdt_no VARCHAR(50), @mold_count INT OUTPUT -- 输出参数 AS BEGIN SELECT @mold_count = COUNT(1) FROM tb_bas_mold WHERE prdt_no = @prdt_no END

调用方式（注意调用时也要加 OUTPUT）：

DECLARE @cnt INT EXEC dbo.sp_get_mold_count @prdt_no = '6063', @mold_count = @cnt OUTPUT -- 现在 @cnt 里就是返回的数量了 PRINT @cnt

2.3 输入输出参数（既进又出）

OUTPUT 参数也可以同时作为输入——调用时传一个初始值进去，过程中修改它，再传出来。

CREATE PROCEDURE dbo.sp_add_test_times @times INT OUTPUT AS BEGIN SET @times = @times + 1 END

2.4 返回值（RETURN）

除了 OUTPUT 参数，存储过程还可以用 RETURN 返回一个整数值，通常用来表示执行状态（0 表示成功，非 0 表示错误码）。

CREATE PROCEDURE dbo.sp_check_mold @mold_no VARCHAR(50) AS BEGIN IF NOT EXISTS (SELECT 1 FROM tb_bas_mold WHERE mold_no = @mold_no) RETURN -1 -- 模具不存在，返回错误码 RETURN 0 -- 成功 END

调用时接收返回值：

DECLARE @ret INT EXEC @ret = dbo.sp_check_mold @mold_no = 'XXX' PRINT '返回值：' + CAST(@ret AS VARCHAR)

2.5 三种"返回数据"方式对比

方式返回数量类型限制典型用途
SELECT 结果集可以多个结果集任意返回查询数据（报表、列表）
OUTPUT 参数可以多个标量值（单值）返回计算结果、状态值
RETURN 返回值只能 1 个只能是 INT返回执行状态/错误码
本脚本（sp_mold_test_task_query）用的就是"SELECT 结果集"的方式——最后一句 SELECT * FROM #t_Result1 把最终数据作为结果集返回给调用方。这是报表查询类存储过程最常见的模式。

三、临时表、表变量与索引

复杂查询中，临时表是性能优化的利器。把大数据量的中间结果缓存起来，避免重复计算。

3.1 临时表的创建

-- 先判断是否存在，存在则删除 IF OBJECT_ID('tempdb..#mold_test_task') IS NOT NULL DROP TABLE #mold_test_task -- 创建临时表 CREATE TABLE #mold_test_task ( sheet_no VARCHAR(50), mold_no VARCHAR(50), trial_date DATETIME, test_times INT ) -- 给临时表建索引（关键！提升后续查询性能） CREATE NONCLUSTERED INDEX IX_#mold_test_task_sheet_no ON #mold_test_task (sheet_no ASC) CREATE CLUSTERED INDEX IX_#mold_test_task_mold_no ON #mold_test_task (mold_no ASC)

临时表命名规则：

  • #表名 — 局部临时表，只在当前会话中有效，会话断开自动删除。
  • ##表名 — 全局临时表，所有会话都能访问，一般用得少。

3.2 临时表 vs 表变量

很多新手搞不清这两者的区别，这是面试高频题，也是实际开发中必须掌握的。

对比项临时表 (#table)表变量 (@table)
定义方式CREATE TABLE #t(...)DECLARE @t TABLE(...)
存储位置tempdb 数据库tempdb 数据库（内存优先，大了落盘）
作用域当前会话（存储过程内及子调用）当前批处理（仅当前语句块）
能否建索引可以随便建（CREATE INDEX）只能有主键/唯一约束（隐式索引）
能否参与事务可以，事务回滚会影响不参与事务回滚
统计信息有，优化器能生成好的执行计划没有，优化器默认行数很少，数据量大时计划可能很差
可以在动态 SQL 中访问可以不行（动态 SQL 是另一个批处理）
数据量建议从几十行到几百万行都行建议 1 万行以内，最好几百行以内
重新编译可能导致存储过程重编译不会

举个表变量的例子：

DECLARE @mold_list TABLE ( sn_code VARCHAR(50) PRIMARY KEY, mold_no VARCHAR(50) ) INSERT INTO @mold_list(sn_code, mold_no) SELECT sn_code, mold_no FROM tb_bas_mold WHERE prdt_no = '6063'
什么时候用哪个？简单判断：
数据量小（几百行以内）、结构简单 → 用表变量，轻量、快、不占 tempdb 太多资源。
数据量大、需要建索引、要在动态 SQL 里用 → 用临时表。
本脚本数据量大、还有索引，所以全部用临时表，这是正确的选择。

3.3 全局临时表 vs 局部临时表

类型写法作用域何时删除适用场景
局部临时表#table当前会话会话结束或 DROP存储过程内中间计算（最常用）
全局临时表##table所有会话最后一个引用它的会话结束跨会话共享数据（极少用，注意并发）

3.4 索引的作用

本脚本给每个临时表都建了索引，这是非常好的实践。

聚集索引（Clustered Index）：数据物理上按索引顺序存储。一张表只能有一个聚集索引。

非聚集索引（Nonclustered Index）：独立于数据的索引结构，指向数据行。一张表可以有多个。

给临时表建索引的好处：

  • 后续 JOIN 时大幅加速
  • WHERE 条件过滤更快
  • GROUP BY / ORDER BY 可以利用索引避免排序
索引不是越多越好！每个索引都要占用空间，而且写入（INSERT/UPDATE/DELETE）时都要维护索引。临时表一般是"一次写入、多次读取"，所以建索引很划算。

四、动态 SQL 拼接

当筛选条件是动态的（用户可能选也可能不选），最灵活的方式就是用字符串拼接 SQL，然后 EXEC 执行。

4.1 基本思路

DECLARE @sql VARCHAR(MAX), @Condition VARCHAR(MAX) -- 初始化条件为空 SELECT @Condition = '' -- 根据参数动态拼接条件 IF @mold_no <> '' BEGIN SET @Condition = @Condition + ' And t.mold_no Like ''%' + @mold_no + '%'' ' END IF @pro_line_no <> '' BEGIN SET @Condition = @Condition + ' And t.testmold_dev = ''' + @pro_line_no + '''' END -- 拼接完整 SQL 并执行 SET @sql = 'SELECT * FROM dbo.tb_mold_trial_detail t WHERE 1=1 ' + @Condition EXEC (@sql)

4.2 几个关键技巧

① WHERE 1=1 的妙用

用 WHERE 1=1 做占位，后面所有条件都可以统一用 AND ... 拼接，不用判断第一个条件要不要加 AND。

② 单引号转义

在字符串里写单引号，要用两个单引号 '' 表示一个单引号。比如：

-- 最终效果：And t.mold_no Like '%abc%' SET @Condition = ' And t.mold_no Like ''%' + @mold_no + '%'' '
动态 SQL 有 SQL 注入风险！如果参数来自用户输入，要做安全校验。本脚本参数都是内部系统传的，所以问题不大。

③ PRINT 调试

脚本中用了 PRINT @sqltext1 来打印拼接好的 SQL，这是调试动态 SQL 的必备技巧。在 SSMS 的"消息"窗口能看到完整 SQL，复制出来单独执行就能排查问题。

4.3 更安全的方式：sp_executesql 参数化

直接拼接字符串有注入风险，更规范的写法是用 sp_executesql 传参数：

DECLARE @sql NVARCHAR(MAX) SET @sql = N' SELECT * FROM dbo.tb_mold_trial_detail t WHERE t.org_no = @org_no AND t.mold_no LIKE ''%'' + @mold_no + ''%'' ' EXEC sp_executesql @sql, N'@org_no VARCHAR(20), @mold_no VARCHAR(50)', @org_no = @org_no, @mold_no = @mold_no

好处：

  • 防 SQL 注入
  • 执行计划可以复用，性能更好
  • 不用处理单引号转义，代码更清爽

五、各种 JOIN 用法

本脚本用到了多种 JOIN 方式，是学习 JOIN 的好例子。

5.1 INNER JOIN（内连接）

只返回两边都匹配的行。

FROM dbo.tb_mold_trial_detail t WITH (NOLOCK) INNER JOIN dbo.tb_bas_mold AS TBM WITH (NOLOCK) ON TBM.sn_code = t.sn_code

含义：只保留"试模任务表中存在，且模具基础表也存在"的记录。如果某个试模任务的 sn_code 在模具表里找不到，这条记录就被过滤掉了。

5.2 LEFT JOIN（左连接）

左表全部保留，右表匹配不上的地方显示 NULL。

LEFT JOIN dbo.tb_mold_trial_conclusion AS TMTC WITH (NOLOCK) ON TMTC.sheet_no = t.sheet_no

含义：所有试模任务都保留，即使还没出检验结论（没有结论记录），结论字段就是 NULL。

5.3 WITH (NOLOCK)

脚本里几乎每个表后面都加了 WITH (NOLOCK)，这是什么意思？

FROM dbo.tb_mold_trial_detail t WITH (NOLOCK)

NOLOCK = 不锁表、不等待锁。读数据的时候不加共享锁，别人改数据也不阻塞你。

好处：查询速度快，不会被阻塞。

坏处：可能读到"脏读"（别人还没提交的数据，如果他回滚了你读的就是错的）。

报表类查询、对数据精度要求不极致的场景，NOLOCK 是常用的性能优化手段。但涉及金额、库存等关键数据不要用。

5.4 JOIN 类型总结

类型效果什么时候用
INNER JOIN只返回两边都匹配的行两表数据都必须存在，比如主表+字典表
LEFT JOIN左表全保留，右表不匹配的为 NULL主数据要全保留，附加信息可能没有
RIGHT JOIN右表全保留（基本不用，都改成 LEFT JOIN 写）—
FULL JOIN两边都保留，匹配不上的为 NULL数据对比、全量合并，很少用
CROSS JOIN笛卡尔积，两边所有组合极少用，一般是写错了

六、OUTER APPLY 与 CROSS APPLY

这是 SQL Server 比较高级的用法，也是本脚本的亮点之一。

6.1 什么是 APPLY

APPLY 可以理解为"对左表的每一行，都执行一次右边的子查询/表值函数"。

  • OUTER APPLY：类似 LEFT JOIN，右表没数据也保留左表行（右边字段为 NULL）
  • CROSS APPLY：类似 INNER JOIN，右表没数据则左表行也被过滤

6.2 脚本中的例子

OUTER APPLY ( SELECT p.product_type, p.show_density, p.difficulty, p.alloy_no + '-' + p.alloy_sta AS alloy_state FROM zgDmp.dbo.tb_bas_product p WITH (NOLOCK) WHERE TBM.prdt_no = p.prdt_no ) p

这个 OUTER APPLY 的效果跟 LEFT JOIN 几乎一样，但写法更灵活——右表可以是一个复杂的子查询。

6.3 什么时候用 APPLY 而不用 JOIN？

  • 右表是一个表值函数（比如 dbo.func_name(col)）
  • 右表需要引用左表的列做 TOP N 过滤
  • 逻辑上更清晰，把一组相关字段封装在一起

再看一个更能体现 APPLY 优势的例子（脚本里的专用垫查询）：

OUTER APPLY ( SELECT STRING_AGG(TMSSP.special_pad_no, ';') AS special_pad_no FROM dbo.tb_mold_set_special_pad AS TMSSP WITH (NOLOCK) WHERE TMSSP.sn_code = t.sn_code ) AS spec_pad

这里把"专用垫编号拼接"的逻辑封装在一个 OUTER APPLY 里，主查询看起来更干净。

七、字符串函数

脚本中用到了不少字符串处理函数，挑几个常用的讲：

7.1 STRING_AGG — 字符串聚合

把多行的值拼成一个字符串，用指定分隔符分隔。

-- 把一个模具的所有专用垫编号用分号拼起来 SELECT STRING_AGG(special_pad_no, ';') AS special_pad_no FROM dbo.tb_mold_set_special_pad WHERE sn_code = @sn_code

结果示例：垫A;垫B;垫C

7.2 CONCAT — 字符串拼接

比用 + 更安全，遇到 NULL 不会返回 NULL，会自动转成空字符串。

-- 拼接文件ID前缀 CONCAT('DMP_', small_pic.file_id) AS small_file_id

7.3 ISNULL — 空值替换

如果第一个参数为 NULL，返回第二个参数。

ISNULL(t.specialpad, spec_pad.special_pad_no) AS specialpad

含义：如果 t.specialpad 不为空就用它，否则用 spec_pad.special_pad_no。

类似的还有 COALESCE，可以接收多个参数，返回第一个非 NULL 的值：

COALESCE(a, b, c, '默认值')

7.4 LIKE — 模糊查询

-- 模具编码包含某值 t.mold_no Like '%' + @mold_no + '%'

% 是通配符，代表任意字符（可以是 0 个、1 个或多个）。

其他通配符：

  • _ — 匹配任意单个字符
  • [abc] — 匹配 a、b、c 中的任意一个
  • [^abc] — 不匹配 a、b、c 中的任意一个

7.5 FORMAT — 格式化

-- 日期格式化 trial_date_day = CAST(FORMAT(a.trial_date, 'yyyy-MM-dd') AS VARCHAR(20)) trial_date_time = CAST(FORMAT(a.trial_date, 'HH:mm:ss') AS VARCHAR(20))

八、日期时间处理

8.1 GETDATE() — 当前时间

-- 模具状态持续时间 = 当前时间 - 状态变更时间 UPDATE #t_Result1 SET mold_status_duration = DATEDIFF(HOUR, sta_time, GETDATE())

8.2 DATEDIFF — 时间差

DATEDIFF(DAY, start_date, end_date) -- 相差多少天 DATEDIFF(HOUR, start_time, end_time) -- 相差多少小时 DATEDIFF(MINUTE, t1, t2) -- 相差多少分钟

脚本中判断试模是否超时：

DATEDIFF(DAY, a.first_down_time, ISNULL(a.check_time, GETDATE())) > oo.time_limit

8.3 DATEADD — 日期加减

DATEADD(DAY, 7, getdate()) -- 7天后 DATEADD(HOUR, -2, getdate()) -- 2小时前

8.4 构造当天起止时间

脚本中的做法：

SET @trial_datetime_beg = TRY_CONVERT(DATETIME, CONVERT(VARCHAR(10), @trial_date_beg) + ' 00:00:00') SET @trial_datetime_end = TRY_CONVERT(DATETIME, CONVERT(VARCHAR(10), @trial_date_end) + ' 23:59:59')

更简洁的写法（SQL Server 2012+）：

SET @trial_datetime_beg = CAST(CAST(@trial_date_beg AS DATE) AS DATETIME) SET @trial_datetime_end = DATEADD(SECOND, -1, CAST(DATEADD(DAY, 1, CAST(@trial_date_end AS DATE)) AS DATETIME))

九、EXISTS 与 NOT EXISTS

EXISTS 用来判断"有没有"，只要子查询返回至少一行，就为真。它比 COUNT(*) 效率更高，因为找到第一行就停止了。

9.1 判断产线是否属于某个组织

AND EXISTS ( SELECT 1 FROM zgDmp.dbo.tb_bas_eqm_line AS TBEL WITH (NOLOCK) WHERE TBEL.eqm_line_no = t.testmold_dev AND TBEL.org_no = '003' )

含义：这条试模任务的产线，必须属于 003 组织。

9.2 EXISTS vs IN

写法示例适用场景
EXISTSWHERE EXISTS (SELECT 1 ... WHERE a.id = b.id)子查询数据量大时更快
INWHERE id IN (SELECT id FROM ...)子查询结果集小时更直观
一般来说，两张表都很大时 EXISTS 性能更好；子查询结果很少时 IN 更直观。实际开发中 EXISTS 用得更多，因为不容易出 NULL 陷阱（IN 的子查询里如果有 NULL 值，整个结果就都不对了）。

十、DELETE / UPDATE 关联写法

10.1 DELETE 带 JOIN / EXISTS

SQL Server 支持 DELETE 时关联其他表做条件判断。

-- 删除未试模但已再利用的记录 DELETE t FROM #mold_test_task t WHERE test_fin_sw = '0' AND EXISTS ( SELECT 1 FROM dbo.tb_bas_mold WHERE sn_code = t.sn_code AND status IN ('127', '250', '140', '214') )

语法要点：DELETE 别名 FROM 表名 别名 ...，先写要删的表别名，再写 FROM 和条件。

10.2 UPDATE 带 JOIN / OUTER APPLY

UPDATE t SET t.mold_cnt = ISNULL(c.mold_cnt, 0) FROM #mold_test_task t OUTER APPLY ( SELECT COUNT(1) AS mold_cnt FROM dbo.tb_bas_mold WITH (NOLOCK) WHERE prdt_no = t.prdt_no AND sn_code <> t.sn_code AND status NOT IN ('127', '250', '140', '214') ) c

这种写法非常实用：从另一个表计算出一个值，更新回主表。比写子查询更灵活。

十一、OUTPUT 子句与 inserted/deleted 表

这是 SQL Server 非常有特色也非常实用的功能，做日志、状态变化判断、批量联动处理时经常用到。

11.1 inserted 和 deleted 是什么

它们是 SQL Server 自动生成的两张特殊临时表，只在触发器或带 OUTPUT 子句的 DML 语句执行期间存在，用来存放"改动前后的数据"。

特殊表含义INSERT 时UPDATE 时DELETE 时
inserted新值 / 新行新插入的行更新后的新值空（无数据）
deleted旧值 / 旧行空（无数据）更新前的旧值被删除的行
记住一个简单规律：UPDATE = 先删旧的（进 deleted），再插新的（进 inserted）。所以 UPDATE 时两张表都有数据，而且行数一样多，通过主键可以一一对应。

11.2 OUTPUT 子句的基本用法

OUTPUT 子句可以加在 INSERT / UPDATE / DELETE 语句后面，把变动的数据直接输出（或存起来）。

最简单的用法——直接输出改动结果：

UPDATE dbo.tb_mes_mold_use SET sj_qualified = '1' OUTPUT inserted.sn_code, inserted.sj_qualified AS new_value, deleted.sj_qualified AS old_value WHERE sn_code = 'M001'

执行后会返回一个结果集，显示改了哪条、改前是什么、改后是什么。

11.3 OUTPUT ... INTO — 把变动存进表变量

更常用的是把变动存进表变量，后面慢慢处理：

DECLARE @UpdatedRows TABLE ( pg_no VARCHAR(50), sn_code VARCHAR(50), mold_no VARCHAR(50), old_sj_qualified CHAR(1), new_sj_qualified CHAR(1), old_reason VARCHAR(200), new_reason VARCHAR(200), old_is_calc BIT, new_is_calc BIT ); UPDATE dbo.tb_mes_mold_use SET sj_qualified = '1', sj_qualified_reason = '尺寸合格', is_calc = 1 OUTPUT inserted.pg_no, inserted.sn_code, inserted.mold_no, deleted.sj_qualified, -- 更新前的旧值 inserted.sj_qualified, -- 更新后的新值 deleted.sj_qualified_reason, -- 旧值 inserted.sj_qualified_reason, -- 新值 deleted.is_calc, -- 旧值 inserted.is_calc -- 新值 INTO @UpdatedRows(pg_no, sn_code, mold_no, old_sj_qualified, new_sj_qualified, old_reason, new_reason, old_is_calc, new_is_calc) WHERE sn_code = 'M001'; -- 后面就可以用 @UpdatedRows 做各种判断了 SELECT * FROM @UpdatedRows;

11.4 典型应用场景

场景一：数据变更日志

每次更新都把"改前什么样、改成了什么样"记到日志表里，方便审计追溯。

UPDATE tb_bas_mold SET status = '10' OUTPUT inserted.sn_code, deleted.status AS old_status, inserted.status AS new_status, GETDATE() AS change_time INTO tb_mold_status_log(sn_code, old_status, new_status, change_time) WHERE sn_code = 'M001';

场景二：判断"首次"状态变化

比如"首次合格"——只有从 0 变成 1 才算，已经是 1 的再改一次不算。

IF EXISTS ( SELECT 1 FROM @UpdatedRows WHERE old_sj_qualified = '0' AND new_sj_qualified = '1' ) BEGIN -- 首次合格，发奖励、更新统计... PRINT '首次合格！' END

场景三：批量操作后拿到受影响的行

一次更新了几百条数据，想知道具体改了哪些，继续做后续处理，OUTPUT ... INTO 一把搞定。

11.5 触发器中的经典用法

OUTPUT 和 inserted/deleted 最常出现在触发器里。下面是一个完整的触发器例子：

CREATE TRIGGER trg_mold_use_after_update ON dbo.tb_mes_mold_use AFTER UPDATE AS BEGIN SET NOCOUNT ON; -- 只有 sj_qualified 字段被更新时才处理 IF UPDATE(sj_qualified) BEGIN -- 找出"首次合格"的行：旧值=0，新值=1 INSERT INTO dbo.tb_mold_first_pass_log (sn_code, mold_no, pass_time, pg_no) SELECT i.sn_code, i.mold_no, i.up_time, i.pg_no FROM inserted i INNER JOIN deleted d ON i.pg_no = d.pg_no -- 主键关联新旧表 WHERE d.sj_qualified = '0' AND i.sj_qualified = '1'; END END
触发器里的 inserted 和 deleted 表是自动存在的，不用你定义，直接用就行。而且它们可能有多行数据（批量更新时），所以一定要用集合思维来写，不要假设只有一行。

11.6 UPDATE() 函数

在触发器里，还可以用 UPDATE(列名) 判断某一列有没有被修改：

IF UPDATE(sj_qualified) -- sj_qualified 列被更新了吗？ BEGIN -- 做合格状态变更的逻辑 END

这样可以避免每次更新任何字段都触发全部逻辑，提升性能。

11.7 注意事项

  • OUTPUT 子句返回的是结果集，可以直接给客户端，也可以 INTO 到表变量/临时表。
  • inserted 和 deleted 表是只读的，你不能改它们的数据。
  • 批量更新时，inserted/deleted 里可能有很多行，触发器里千万不要写"假设只有一行"的逻辑。
  • INSTEAD OF 触发器也用这两张表，用法类似。

十二、子查询与 TOP 1 技巧

脚本中大量使用了 TOP 1 ... ORDER BY 的子查询模式，这是取"最新一条"或"最早一条"的经典写法。

11.1 取首次下架时间

( SELECT TOP (1) a.trial_off_date FROM dbo.tb_mold_trial_detail a WITH (NOLOCK) WHERE a.sn_code = t.sn_code AND a.trial_nowcount = 1 AND a.trial_date <= t.trial_date ORDER BY a.trial_date DESC ) AS first_down_time

逻辑拆解：

  1. 找到同模具（sn_code 相同）
  2. 第 1 次试模（trial_nowcount = 1）
  3. 不晚于当前试模日期（trial_date <= t.trial_date）
  4. 按日期倒序，取第一条（也就是最近的那一次第1次试模）

11.2 相关子查询 vs 独立子查询

类型特点例子
相关子查询子查询引用了外层表的列，每行都要执行一次上面的 first_down_time
独立子查询子查询跟外层无关，只执行一次SELECT MAX(price) FROM products
相关子查询如果外层数据量大，性能可能很差（每行执行一次）。优化方式：改用 JOIN + 分组，或者先聚合到临时表再 JOIN。

十三、TRY_CONVERT 安全转换

SET @trial_datetime_beg = TRY_CONVERT(DATETIME, CONVERT(VARCHAR(10), @trial_date_beg) + ' 00:00:00')

TRY_CONVERT 和 CONVERT 的区别：

  • CONVERT：转换失败就报错，整个语句中断
  • TRY_CONVERT：转换失败返回 NULL，不报错

这是 SQL Server 2012 开始有的函数，处理外部传入的参数时非常好用，避免因为格式不对整个存储过程崩掉。

类似的还有：TRY_CAST、TRY_PARSE。

十四、整体架构与优化思路

14.1 这个脚本的整体设计模式

脚本的结构可以概括为"三阶段填充"：

阶段做什么写入哪个临时表
第一阶段从主表取试模任务核心数据，关联产品、模具、产线等基础信息#mold_test_task
第二阶段补充模具档案信息、计算待挤压量、加载机台参数#mold_info、#need_jy_qty、#jy_dev
第三阶段所有数据整合，补充字典名称、时限标准、设备参数等，生成最终结果#t_Result1

14.2 为什么要分这么多临时表？

  • 性能：每一步数据量都在缩小，后面的 JOIN 更快
  • 可调试：每个阶段都能单独 SELECT 出来看，排查问题方便
  • 逻辑清晰：每个临时表职责单一，可读性好
  • 索引加持：临时表上可以建索引，比复杂的子查询执行计划更可控

14.3 可以继续优化的地方

① 动态 SQL 的注入风险

目前参数是直接拼进字符串的。更安全的写法是用 sp_executesql 参数化（见第四章第 4.3 节）。

② 相关子查询改 JOIN

first_down_time、first_test_time 这些每行执行一次的子查询，如果数据量大可以改成先分组算好再 JOIN。

③ 索引检查

主表 tb_mold_trial_detail 的 sn_code、mold_no、trial_date 等字段上是否有合适的索引，对性能影响很大。可以用 SSMS 的"包括实际执行计划"功能查看有没有"索引扫描"、"键查找"等慢操作。

14.4 学习路线建议

  2. 然后学子查询、EXISTS、临时表
  3. 再进阶到动态 SQL、窗口函数（ROW_NUMBER 等）
  4. 最后学习执行计划分析和性能调优
